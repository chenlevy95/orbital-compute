01 / From workbook to publication

Be flexible about layout. Be strict about meaning.

The filename supplies the observation date. The contract’s start and end dates supply its business term. Archive the received file first. Validate its contents separately, and publish only complete, usable contract snapshots.

1 · ARCHIVE

Commit the received bytes

Store each filename + checksum once, before parsing. Files start as pending. Their original contents survive validation failures and later crashes.

2 · DETECT

Find the real table

Find one unambiguous essential-header row: contract/customer IDs, start/end dates, and amount. Name and status are optional. Use reviewed aliases, independent of column position.

3 · NORMALIZE

Validate business fields

Normalize IDs, dates, and amounts. Keep extras and column-presence flags. An essential-field failure quarantines the entire snapshot with diagnostics; other valid files can proceed.

Publication transaction · archived evidence already committed
4 · RECHECK

Compare snapshot identity

Matching published files are no-ops. Different bytes for a published date are quarantined. A corrected file for an unpublished date may be accepted. Recheck under the writer lock.

5 · RECONSTRUCT

Preserve & derive history

Insert candidate observations and rebuild versions chronologically. Carry disappeared contracts forward. Validate all published dates, including later states affected by an older arrival.

6 · PUBLISH

Whole snapshots only

Accepted snapshots update observations and history together. Failed candidates are rolled back and quarantined without blocking valid files. Readers never see half an updated history.

Why no fuzzy header matching? A guessed financial column can silently change the meaning of a number. An unfamiliar essential header quarantines the file. Review the mapping, then use --reprocess to retry its archived bytes.
Archive states: pending → published or quarantined. A valid corrected file for an unpublished date can mark earlier rejected variants superseded. Unresolved quarantine returns exit 1, even if another file published successfully.
02 / History is about what we observed

Observation time ≠ contract time

SCD Type 2 means keeping a new version when tracked values change, instead of overwriting the old version. Observation intervals are half-open: [observed_from, observed_to). Contract end dates remain inclusive.

The supplied exports contain 9 + 10 + 10 unique contract observations. There are 11 distinct contracts across the archive; the missing expired contract remains in the current view.

Why 29 observations, but only 16 versions?

July creates 9 initial versions. August adds 3: K-1001’s name change, K-1009’s amendment, and new K-1010. September adds 4: status changes for K-1003, K-1006, and K-1010, plus new K-1011. Repeated terms create observations, not versions. September’s duplicate K-1008 row is collapsed; its original rows remain in the workbook archive.

The invariant: applying the same input twice has the same business result as applying it once. For accepted and quarantined replays, stored state stays unchanged. Quarantined input is retried explicitly with --reprocess. Logs may differ. The existing usage loader can update operational full-scan timestamps while leaving business results identical.
04 / Separate evidence from interpretation

Evidence survives even when validation fails.

The original file explains what Finance sent. Observations explain how it was parsed. History explains which core values changed. The current view supports future calculations using latest known terms.

1. Received files

commitment_files

Key: filename + checksum
Original bytes, state, errors, warnings, layout.

Includes rejected files. commitment_snapshots separately records the one published file for each date.

2. Observations

commitment_observations

Key: date + contract ID
Normalized fields, missing-column flags, extras, source row references.

One contract per published export. Quarantined files create no observations.

3. Versions

contract_history

Key: contract ID + observed start
Core values, observed start, exclusive observed end.

Last version stays open, even if the tracker drops the contract.

4. Current view

contracts_current

One row: per known contract
Select its open-ended history version.

Includes expired contracts. Active dates come from the term, not row presence.

What creates a core version?

Changes to customer ID, dates, amount, or supplied name/status. An absent descriptive column retains its previous known value. An explicitly empty cell sets NULL and can create a version.

What stays only in observations?

Owner, region, notes, and future extras stay auditable without inflating history. Missing name/status columns are recorded in missing_fields_json. Missing essential terms are never filled from earlier snapshots.

05 / Crash and concurrency boundaries

The commit is the publication boundary.

Archive bytes first, parse outside the publication lock, then recheck and publish under it. A failed publication leaves durable pending evidence for recovery.

WAL lets readers use the previous committed snapshot while a writer works. SQLite still has only one writer. A contender waits for a bounded time, then fails cleanly if the lock is unavailable.

Tracker and usage ingestion are separate transactions. Atomic publication across both sources and future utilization tables needs a later orchestration design.
06 / Why this design

Small enough to explain. Strict enough to trust.

Design choices, benefits, and alternatives
DecisionWhat it buysTradeoff / alternative
SQLiteNo database server; transactional and portable.Single writer and local persistent storage. PostgreSQL is a better fit for distributed workers.
Archive + observations + SCDAuditable source, reproducible parsing, simple current-term queries.More storage than SCD alone. Observations alone are simpler but shift version derivation to readers.
Explicit header aliasesReordering and known renaming are safe.Unfamiliar required headers need review. Fuzzy matching reduces interruptions but can choose the wrong field.
Reconstruct history on new snapshotsLate older files yield the same history as a chronological full load.Work grows with retained observations. Incremental history maintenance is faster at scale but more complex.
Immutable published datesRaw variants remain archived; accepted history cannot silently change.Corrected quarantines can publish, but different bytes for an already published date need a separate correction workflow.
Quarantine whole snapshotsValid files proceed; invalid files remain available without publishing partial rows.Track both received and published dates. Last-known terms may be stale while a newer export is quarantined.

Acceptance checks

  • Run twice: compare all persisted rows and query results.
  • Incremental load equals a fresh load.
  • Shuffled input and late older snapshots yield identical history.
  • Missing contracts and exact duplicate rows are handled safely.
  • Inclusive renewal boundaries do not overlap.
  • Conflict, crash, and concurrent-run tests preserve atomicity.
  • Missing optional columns differ from explicit empty cells.
  • Reprocessing and migration preserve archived evidence.
  • Existing usage tests still pass; usage records stay unchanged.
