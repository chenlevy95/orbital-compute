Orbital Ingestion Flow
orbital-compute · ingestion and models

How data gets into the database, and what comes out

Two loaders, one SQLite file, one model build. ingest_usage.py pulls daily spend from the billing API. ingest_commitments.py reads Finance's Excel snapshots. build_models.py turns both into daily contract utilization and on-demand spend. Each script writes to storage/usage.sqlite3 in a single transaction.

The big picture

Sources, loaders, tables, models

ingest_usage.py

Usage loader: one run, step by step

The whole run sits inside one BEGIN IMMEDIATE transaction. It takes the write lock first, so a second run started at the same time waits instead of interleaving. If anything fails, or the pod is killed, SQLite rolls back and the database looks exactly like before the run.

ingest_commitments.py

Commitments loader: parse everything, then write

Every workbook is parsed and validated before the database is opened. Then the loader takes the write lock and adds each new snapshot inside its own savepoint, rebuilding the full history each time. A bad file is skipped and reported, the other files still load, and the run exits 1. Once the bad file is fixed, the next run loads it.

Status warnings

Finance's status column is typed by hand, so the models ignore it and go by the dates. After every run the loader checks each contract's latest version against the last snapshot it appeared in. It warns about anything suspicious but never blocks the run. The warning repeats on every run until Finance fixes the tracker.

In the trackerLoaderModels
Expired or Cancelled, end date still after the snapshotwarningStill tracked by its dates. Finance corrects the end date or the label.

The supplied snapshots raise no warnings.

build_models.py

Models: from spend to utilization

The build reads each contract's latest terms and each customer's daily non-void spend. It then deletes both model tables and rebuilds them from scratch, inside one BEGIN IMMEDIATE transaction. Readers keep seeing the previous tables until the commit. A killed build changes nothing, and a rerun on the same inputs produces identical rows.

Why rebuild everything each run

Past rows don't stay correct. Appending only today's row would leave all of these wrong.

What happensRows that change
Billing restates or voids a record up to 30 days backThat day, plus every later running total and projection
Usage arrives late (C008, 8 days)A row first written as $0, and everything after it
Finance amends terms (K-1009: $500k → $650k, end moved to Jan 31)Every row of the contract, back to its start date
A new contract appears in a snapshotRows back to its start date, and attribution for those days

At about 1,600 rows the rebuild takes milliseconds. An incremental build would have to track each of these cases.

Rules the build follows

  • A contract is active when start_date ≤ day ≤ end_date. Both dates are inclusive, and status is never used.
  • Every day of the term gets a row, including days with no spend.
  • A contract that starts after the last loaded day has no rows yet.
  • Spend is summed as exact decimals. Expected and projected spend are rounded to cents, and utilization_pct to 6 decimal places.
  • utilization_pct is a ratio, where 1.0 means on track. It isn't multiplied by 100.
  • at_risk is decided before rounding, so rounding can never flip it at the 0.9 line.
Failure and concurrency

What happens when things go wrong

SituationWhat happens
Pod killed mid-runThe transaction never committed, so SQLite discards it. The next run starts the same scan again.
Two runs at the same timeThe second waits on the write lock (up to 60 s), then sees the first run's data and finds nothing new.
API returns 429 or 503Up to 6 attempts with growing, jittered waits, at least as long as Retry-After.
Token expiresRefreshed 5 s before expiry, and once more after a 401.
Finance renames a columnThat file is skipped and the error names the missing header. The other files still load. Confirm the meaning, add it to ALIASES, and rerun to backfill it.
Finance sends a broken file, then a fixed oneThe broken file is skipped and never stored. The fixed file, under the same date, loads on the next run, and the history rebuild puts it in date order.
A status contradicts the datesThe loader prints a warning on every run and still loads the file. The models keep going by the dates.
A record arrives more than 30 days lateOutside the overlap, so it's missed until someone runs --reconcile. Measured: none did.
Model build killed, or run twice at onceRolled back, or queued on the lock. Readers see the old tables or the new ones, never a mix.
